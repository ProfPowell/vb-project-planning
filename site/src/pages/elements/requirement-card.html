Overview

The <requirement-card> component is a display-only tile for a single Non-Functional Requirement (ility) row — performance, security, accessibility, observability, and so on. It renders the chosen priority, a rationale, and an optional conflict flag for status dashboards, ADR appendices, and review surfaces.

The prioritization decision happens in <quality-target>. Use <requirement-card> downstream of that decision — in the documents that consume the choice. It is shadow-DOM encapsulated, with the ility name, an optional badge, the rationale, and any conflict note supplied through named slots.

Basic example

Performance SLA

Pages must paint LCP < 2.5s on 3G — a hard ad-network constraint.

 Accessibility

WCAG 2.2 AA across all customer-facing flows.

 Internationalization

English-only at launch; defer i18n to v2.

Conflicts with the marketing team's APAC-launch ask — needs an ADR.

How it works

The data-priority enum drives a :state(priority-*) hook, the default pill text, and the accent color. Add data-conflict to flag a drift or contradiction note; the card renders an emphasized border and exposes the conflicts slot. The card is inert by default — set tabindex="0" (or wrap it in an <a> / <button>) to make it activatable, at which point it emits requirement-card:click with { priority, hasConflict, originalEvent }.

The card never navigates by itself. Listen for requirement-card:click to route, or wrap it in an <a href> and let the link navigate while the event still fires for analytics or in-app routing.

Slots

SlotDescription
nameIlity label (e.g. "Performance").
badgeCategory / version / source tag, shown as small uppercase muted text.
priority-pillYour own pill. When empty, a default pill renders from data-priority.
rationaleWhy this priority was chosen (especially for Critical rows). The row collapses when empty.
conflictsShort conflict / drift note, usually paired with data-conflict. The row collapses when empty.

CSS parts

The card renders in shadow DOM, so style its insides with ::part(): card, head, name, badge, pill, priority-default (the generated pill), rationale, and conflicts.

requirement-card::part(priority-default) { letter-spacing: 0; text-transform: none; }

Accessibility

  • Never colour-only. Priority is conveyed by the pill's text label, not by accent colour alone, so the critical / important / acceptable / not-relevant distinction survives for low-vision and colour-blind readers. The conflict note is real slotted prose, so screen readers announce why a row is flagged rather than just seeing an emphasized border.
  • Opt-in interactivity. The card stays non-interactive (no spurious focus stop) until you opt in.
  • With tabindex. The card gets role="button" (unless you set your own role) and activates on click, Enter, and Space. Give it an accessible name that says where it goes if the slotted name isn't enough.
  • Wrapped in <a href> / <button>. The native element supplies the role and focus. Its own keyboard activation fires the event too, so mouse, keyboard, and touch all behave the same. Don't also add tabindex to the card in this case, or keyboard users hit two focus stops.
